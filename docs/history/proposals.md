## FR-010 多帖参与者对比

### 目标

一次抓了多个帖子后，能看出谁参加了哪些帖子、谁只在某帖出现。

### 入口

「帖子统计」→「表格查看」→ 新增子表「参与者对比」。

### 基本流程

1. 列出当前已抓的帖子（标题 + 吧名 + 楼层数）；
2. 勾选至少 2 个帖子；
3. 选择对比方式；
4. 生成对比表；
5. 可排序、复制、导出。

### 对比方式（待选）

- **方案 A：固定四种**
  - 交集：在所有选中帖子都出现；
  - 并集：在任意选中帖子出现；
  - 仅在 A：只在第一个选中帖出现；
  - A − B：在 A 出现、不在 B 出现。
- **方案 B：任意表达式**
  - 每个帖子有“包含 / 排除”开关；
  - 例如：A 包含、B 排除、C 包含；
  - 灵活但学习成本高。
- **方案 C：只做交集 / 并集**
  - 最简单，但“只在某帖”这种常见需求做不了。

推荐：**A**。

### 身份匹配

- 优先用户 ID；
- 没有 ID 时回退用户名；
- 再没有回退昵称；
- 同一帖子内同一用户只算一次。

### 结果表

| 列 | 说明 |
|---|---|
| 昵称 | 显示名 |
| 用户名 | 原始用户名 |
| 用户 ID | 贴吧 ID |
| 帖子 A | 在 A 的楼层+楼中楼数 |
| 帖子 B | 在 B 的楼层+楼中楼数 |
| 合计 | 各帖合计 |
| 类型 | 交集 / 仅 A / 仅 B |

### 边界

- 少于 2 个帖子：提示先抓并勾选；
- 某个帖子没有参与者：显示空结果并提示；
- 同名不同人：按 ID/用户名区分；
- 未抓到 ID 的用户：标注“ID 未知”，匹配可能不精确；
- 对比结果不受当前参与者筛选影响。

### 验收

- 两个帖子交集人数正确；
- “仅 A”不包含 B 的人；
- 导出结果与屏幕一致；
- 排序、复制可用。

### 导出

- 导出当前对比结果（仅此表）；
- 表头、合计行、超链接（可选）。

## FR-011 单用户报告导出

### 目标

把某一个人的资料、关注、最近发言、参与帖子导出成一份独立报告，方便存档或发人。

### 入口（建议两个）

- 「查用户」页：查询后点「导出报告」；
- 「参与者」页：选中某人 → 右键「导出此人报告」。

### 报告内容

一个 Excel 工作簿，包含：

1. **基本信息**
   - 昵称、用户名、用户 ID、等级、粉丝、关注数、发帖数；
   - 数据来源模式（免登录 / 登录）；
   - 导出时间。
2. **关注贴吧**
   - 吧名、等级；
   - 是否来自隐藏恢复；
   - 免登录时标注“可能不完整”。
3. **最近发言**
   - 日期、类型、贴吧、标题、内容、链接。
4. **本帖参与**
   - 在当前抓取结果里的楼层数、楼中楼数、合计；
   - 首次出现楼层。
5. **本地标记**（仅在启用时）
   - 颜色、命中吧名；
   - 关闭时不写。

### 格式（待选）

- **方案 A：Excel 多工作表**（推荐）
  - 结构清晰，适合存档和发人。
- **方案 B：Excel + Markdown**
  - Excel 给人看，Markdown 方便贴到聊天/文档。
- **方案 C：只 Markdown/文本**
  - 轻量，但不适合表格数据。
- **方案 D：PDF**
  - 好看但生成和排版成本高，中文字体麻烦。

### 命名

```text
用户报告_昵称_用户ID_20261019.xlsx
```

昵称含 emoji 时用 `[U+XXXX]` 代码或用户 ID 替代，避免文件名非法。

### 隐私

- 报告只在本机生成；
- 不包含 Cookie；
- 本地标记默认不写，只有启用时才写；
- 报告里的链接是公开贴吧链接。

### 验收

- 查用户页能导出；
- 参与者页能导出；
- 内容与界面一致；
- 免登录时关注表有“可能不完整”提示。

## FR-012 配置备份 / 恢复

### 目标

换电脑、重装、误删后，能恢复设置和本地标记，不用重新配。

### 入口

「设置」→「通用」→「备份配置 / 恢复配置」。

### 备份范围（待选）

- **方案 A：设置 + 本地标记**（推荐）
  - 颜色开关、模式、红绿灯开关；
  - 本地标记三级名单；
  - 不含 Cookie、不含快照。
- **方案 B：A + Cookie**
  - Cookie 用 DPAPI 加密，换电脑/换账户无法解密；
  - 风险高，不推荐默认包含。
- **方案 C：全部**
  - 再加抓取历史/快照；
  - 文件大，恢复逻辑复杂。

### 文件格式（待选）

- **方案 A：单个 JSON**（推荐）
  - 可读、可版本化、体积小；
  - 恢复前可预览内容。
- **方案 B：ZIP**
  - 可附带说明文件、多个 JSON；
  - 不直观。
- **方案 C：JSON + ZIP 都支持**
  - 灵活但实现成本高。

### 恢复流程

1. 选择备份文件；
2. 显示预览：
   - 模式；
   - 本地标记数量；
   - 备份时间；
3. 提示“会覆盖当前设置和本地标记”；
4. 覆盖前自动生成一份当前配置的临时备份；
5. 确认后写入；
6. 提示“恢复成功，重启后完全生效”。

### 安全

- 默认不含 Cookie；
- 如果用户选择含 Cookie，必须二次确认，并说明“换电脑无法解密”；
- 备份文件不自动上传。

### 验收

- 备份后修改设置，再恢复，设置回到备份时；
- 本地标记数量一致；
- 损坏/非法 JSON 不覆盖现有配置；
- 恢复前有预览和确认。

## FR-014 免登录全量楼中楼（草案）

### 背景

之前免登录只抓每层前 10 条，是因为用了帖子页接口
`/c/f/pb/page?cmd=302001` 的 `floor_rn` 预览字段。

实测 `/c/f/pb/floor?cmd=302002` 可以在无 BDUSS 时按 `pn` 翻页：

- 某层 32 条回复；
- `pn=1` 返回 29 条；
- `pn=2` 返回 2 条；
- `has_more=false`。

所以“10 条”是实现选择，不是匿名接口上限。

### 目标

免登录模式也能抓完整楼中楼，同时控制请求量和失败影响。

### 基本流程

```text
page 接口拿到楼层 + floor pid
  → 先用 sub_post_list 填充前 10 条
  → 对每层请求 floor 接口 pn=1..N
  → 按 pid 去重合并
  → 达到 has_more=false 或上限
  → 写入 ThreadData
```

### 关键选项（待确认）

#### A. 默认抓取深度

- **A1：默认全部，可限条数**（推荐）
  - 默认抓完整；
  - 提供“每层最多 N 条”（10 / 50 / 100 / 全部）。
- A2：默认每层 10 条，用户手动开“全量”
  - 快，但默认不完整。
- A3：只提供“全量 / 前 10”两档
  - 简单，但不够灵活。

#### B. 请求方式

- **B1：逐层顺序，单请求**（推荐）
  - 稳，风控低；
  - 慢，100 层可能几分钟。
- B2：少量并发（2~3）
  - 快，但更容易触发风控。
- B3：并发可配置
  - 灵活，但增加实现和测试成本。

#### C. 登录模式是否也改用 floor 接口

- **C1：只改免登录，登录保持现状**（推荐）
  - 风险最小；
  - 两种模式实现不同。
- C2：两种模式统一用 floor 接口
  - 代码更统一，但登录模式改动大。
- C3：优先 floor，失败回退网页
  - 兼容性最好，逻辑最复杂。

### 推荐默认

```text
深度：全部 + 可限条数
请求：逐层顺序
登录：保持现状，只改免登录
失败：保留前 10 条预览，标注“该层不完整”
```

### 性能与保护

- 每层最多翻 50 页，防止异常死循环；
- 单个帖子最多 2000 次楼中楼请求，超过则停止并提示；
- 每页之间沿用请求间隔；
- 支持中途停止；
- 每层失败重试 1~2 次，仍失败则记录警告，不中断整个帖子。

### 进度与日志

```text
楼中楼：12/43 层，已抓 320 条
第 13 层：32 条（2 页）
第 14 层失败：保留前 10 条
```

### 数据与去重

- 以评论 `pid` 去重；
- 保留 `floor_no`、`floor_author`、`reply_to`、`is_op`、等级、时间；
- 与 page 预览合并时，预览条目优先保留，缺的补进来。

### 测试

- 合成 fixture：某层 35 条，分 2 页（30+5）；
- 去重：预览 10 条 + 翻页 35 条，最终 35 条；
- 失败：第 2 页失败，保留第 1 页并加警告；
- 停止：翻页中途停止，不抛出异常；
- 上限：超过最大页数/请求数时停止并提示。

### 验收

- 32 条回复的楼层，免登录能抓到 31/32（删除的 1 条抓不到）；
- 无重复评论；
- 失败楼层有明确警告；
- 停止按钮有效；
- 不发送 Cookie。
